# 软件更新与发行方案

> 目标：已经装了 CUKTECH 的人，在你不主动联系的情况下也能拿到新版。
> 状态：**已实现（v1.7.0）**。托管渠道最终定为 GitHub Releases。
> 适用版本：v1.7.0 起内置；**v1.6.0 及更早的版本没有任何更新通道**。
> 实现位置：`desktop/updater.py`（客户端）、`desktop/updatecfg.py`（仓库地址）、
> `build_installer.py` → `--publish`（发布）。

---

## 0. 结论摘要

| 项 | 决定 |
|---|---|
| 更新形态 | 启动时检查 → 托盘/浮层提示 → 用户点「立即更新」→ 自动下载校验 → 退出并静默覆盖安装 → 自动回启 |
| 清单协议 | 单个 `update.json`，**安装包地址由清单动态给出**（换 CDN 不用发版） |
| 完整性校验 | 强制 SHA256（无代码签名证书，哈希是唯一防篡改手段） |
| 托管 | **GitHub Releases**（清单走 `releases/latest/download/update.json`，地址永不变化） |
| 第一版必须做 | **是**。老版本没有检查逻辑，之后发多少包都收不到 |

### 为什么最终选 GitHub Releases

- **完全免费，且 URL 天然固定**：`releases/latest/download/update.json` 永远指向最新正式
  release，所以换包、换版本、换镜像都不用改代码 —— 这一条抵消了「国内下载慢」的主要顾虑，
  反正安装包地址是从清单里读的，将来想加国内镜像只改清单内容，不用发版。
- 发版全自动：`build_installer.py --publish` 调 `gh release create/upload`，一条命令完成。
- 代价：55 MB 包国内下载速度不稳，失败率比对象存储高。客户端已经做了「下载失败重试 +
  提示稍后再试 + 保留重试按钮」，最坏情况是用户多点一次或去 Releases 页手动下。
- 若以后用户量上来、下载失败率明显偏高，把清单里的 `downloads` 加上 COS/OSS 地址即可，
  **客户端不用改**。

## 1. 现状（已核实）

- 全仓库无更新检查代码；`grep update/升级/新版本` 的命中都是无关词。
- 分发方式：`分发\` 整个文件夹拷给对方（U 盘 / 微信 / 网盘）。
- 程序装在 `%LOCALAPPDATA%\Programs\CUKTECH`，数据在 `%LOCALAPPDATA%\CUKTECH`。
- 安装器支持 `/S` 静默安装，装完自己 `Popen` 拉起 exe。
- 卸载信息写 `HKCU\...\Uninstall\CUKTECH`，含 `DisplayVersion` / `InstallLocation`。
- 单实例互斥 `Local\CUKTECH_Desktop_Manager`；多角色入口 `--service / --widget / --collect`。
- **无代码签名证书**（`CUKTECH.spec` 里没有签名步骤）。

### 三个已经具备的前提

| 前提 | 为什么重要 |
|---|---|
| 数据目录与程序目录分离，`do_install` 只清程序目录 | 覆盖安装**不丢凭据**（`.env`）、不丢历史功率 |
| 安装器 `/S` 可用，且装完自动启动新 exe | 用户视角是"窗口关一下又回来"，不用手动操作 |
| 卸载键里有 `DisplayVersion` | 能区分安装版/绿色版，绿色版不自动更新 |

## 2. 方案选型

| 档位 | 用户怎么知道 | 投入 | 结论 |
|---|---|---|---|
| A 手动分发 | 你发链接，对方自己装 | 0 | 只适合熟人小范围 |
| **B 提示 + 一键更新** | 托盘/运行管理出现「有新版本」 | 约 220 行，半天 | **采用** |
| C 后台静默升级 | 完全无感 | 要处理并发、断电、回滚 | 用户上千再说 |

### 为什么不用 C（静默升级）

- 用户很可能正在充电、正在看曲线，突然重启会以为软件崩了。
- 静默失败无感知：装坏了用户只会觉得"这软件自己坏了"，你连日志都拿不到。
- 这个软件是常驻托盘工具，用户对"它在动"很敏感，主动确认更安全。

---

## 3. 必须现在就做的理由

`update.json` 的地址是**编译进 exe 的常量**。v1.6.0 没有这段代码，就没有任何办法通知它。所以：

- 第一版（v1.7.0）就把检查逻辑和地址写死。
- 以后要换托管渠道，靠「清单里给的下载地址」解耦 —— 换 CDN 只改清单，客户端不用发版。
- 万一清单地址本身要换，只能发一版「双地址迁移版」：新版同时试新旧地址，老地址保留至少两个版本周期。

## 4. 清单协议 `update.json`

```json
{
  "channel": "stable",
  "version": "1.7.0",
  "min_version": "1.0.0",
  "pub_date": "2026-11-10",
  "notes": [
    "自动启动移到设备设置的场景设置里",
    "新增更新检查"
  ],
  "downloads": [
    {
      "url": "https://xxx.cos.ap-shanghai.myqcloud.com/cuktech/CUKTECH-Setup_v1.7.0.exe",
      "sha256": "9f2c...（64 位小写十六进制）",
      "size": 58134854
    },
    {
      "url": "https://github.com/xxx/releases/download/v1.7.0/CUKTECH-Setup_v1.7.0.exe",
      "sha256": "9f2c...",
      "size": 58134854
    }
  ]
}
```

### 字段约定

| 字段 | 必填 | 说明 |
|---|---|---|
| `version` | 是 | 三段数字，不带 `v` 前缀 |
| `min_version` | 否 | 低于此版本必须更新（协议不兼容时用），默认不过期 |
| `downloads[].url` | 是 | 按顺序尝试，第一个下成功就用 |
| `downloads[].sha256` | 是 | 校验不过就删文件，不装 |
| `downloads[].size` | 是 | 下载前检查磁盘空间，也给进度条用 |
| `notes` | 否 | 字符串数组，浮层里逐条显示 |

### 版本比较（不能用字符串比）

```python
def _vtuple(v: str) -> tuple[int, ...]:
    return tuple(int(x) for x in v.split(".") if x.isdigit())

def is_newer(remote: str, local: str) -> bool:
    a, b = _vtuple(remote), _vtuple(local)
    n = max(len(a), len(b))
    return a + (0,) * (n - len(a)) > b + (0,) * (n - len(b))
```

字符串比较会让 `"1.10.0" < "1.9.0"`，这是这类功能最常见的线上事故。

## 5. 客户端时序

```
启动
 │
 ├─ 40s 后（避开 BLE 连接高峰）
 │   └─ 读本地 update_state.json，距上次检查 <24h 就跳过
 │
 ├─ GET update.json（显式禁用系统代理，逐个源尝试，3s 超时）
 │   ├─ 失败 → 静默跳过，只写日志，不弹任何东西
 │   └─ 成功 → 比较版本
 │        └─ 不比本地新 → 记录检查时间，结束
 │
 ├─ 有新版本 → 标记状态（托盘图标加小点 / 浮层出现一行「有新版本 v1.7.0 →」）
 │
 └─ 用户点「立即更新」
     ├─ 检查磁盘剩余 > size × 2
     ├─ 下载到 %LOCALAPPDATA%\CUKTECH\updates\xxx.exe.part
     ├─ 校验 SHA256 ← 不匹配：删文件，提示"安装包校验失败"，终止
     ├─ 改名为 xxx.exe
     ├─ 启动 CUKTECH.exe --update-runner <setup> <sha256>
     │    （DETACHED_PROCESS | CREATE_BREAKAWAY_FROM_JOB，脱离父进程）
     └─ 主程序 quit()：停 service/widget → 关 WebView2 → 释放 mutex → 退出
          │
          ▼
     --update-runner 进程
          ├─ 等主进程消失（轮询 tasklist，最多 30s）
          ├─ 再校验一次 SHA256（防下载后被替换）
          ├─ 运行 setup.exe /S
          ├─ 退出码非 0 → 写日志 + 保留安装包，下次启动浮层提示"更新失败，可重试"
          └─ 安装器自己 Popen 新 exe（现有逻辑）
```

### 为什么必须有 `--update-runner`

`installer.do_install()` 第一步是 `kill_running()`：`taskkill /IM CUKTECH.exe`，等 3 秒不响应就 `/F` 强杀。

强杀会留下 WebView2 孤儿进程占住 `_internal` 里的 dll，而 `do_install` 清理旧文件是 `except OSError: pass` —— **被占的文件直接跳过**，结果是新旧文件混装。这类故障表现为"更新完某些功能还在跑旧代码"，极难排查。

所以顺序只能是：**主程序自己退干净 → 外部进程触发安装**。现有 `--service / --widget / --collect` 的多角色入口正好能塞下第四个角色，不需要新 exe。

## 6. 代码改动清单

| 文件 | 改动 | 规模 |
|---|---|---|

| `main.py` | 新增 `--update-runner` 分支（放在 `--collect` 之后、`else` 之前） | ~25 行 |
| `desktop/manager.py` | `snapshot()` 加 `update` 字段；`_build_tray()` 加「检查更新…」；启动后起一个 40s 延迟的检查线程 | ~40 行 |
| `console_overlay.js` | 运行管理浮层加一行「版本 / 更新」（与场景设置同样式的条状项） | ~50 行 |
| `cuktech.py` | `GET /api/update` 返回缓存状态（网页版可见；可选） | ~20 行 |

新增本地状态文件 `%LOCALAPPDATA%\CUKTECH\update_state.json`：

```json
{"last_check": 1762400000, "seen_version": "1.7.0", "last_result": "ok"}
```

放独立文件而不塞进 `config.json`：它纯机器状态，写坏了不影响用户设置。

## 7. 安装器要顺手修的地方（重要）

`installer.main()` 静默分支现在是：

```python
if silent:
    do_install(create_desktop=True, autostart=True)
```

两个副作用在「自动更新」场景下会被放大：

1. **用户关掉的开机自启会被重新打开**。应用侧 `desktop/autostart.py` 和安装器共用同一个 `HKCU\...\Run\CUKTECH` 值，`/S` 无条件写回 = 用户的选择被覆盖。
2. **用户删掉的桌面快捷方式会重新出现**。

改法：`/S` 且 `is_installed()` 为真（= 覆盖安装）时，读一下现有状态再沿用：

```python
if silent:
    first = not is_installed()
    do_install(create_desktop=first or has_desktop_shortcut(),
               autostart=first or autostart_enabled())
```

首次安装（`first=True`）仍保持现在的默认行为，不动老用户体验。

> 另外记一笔：安装器写自启命令是 `"exe" --silent`，应用侧写的是 `"exe" --manager --silent`。`main.py` 的 `--manager` 会被忽略（走 `else` 分支），所以功能上都正常，只是同一个值有两种写法，建议统一成 `--manager --silent`。

## 8. 异常分支

| 场景 | 行为 |
|---|---|
| 清单拉不到 / 404 / 超时 | 静默跳过，24h 后再试，**不弹窗不报错** |
| 清单 JSON 结构坏了 | 同上，日志记一条 |
| 版本号解析失败 | 跳过本次 |
| 下载中断 | 最多重试 2 次（换下一个镜像），仍失败则提示"网络不稳，稍后再试" |
| SHA256 不匹配 | 删文件，提示"安装包校验失败"，**绝不安装** |
| 磁盘空间不足 | 下载前就拦住，提示需要多少空间 |
| 用户正在充电时点更新 | 允许；安装过程不影响数据（数据不在程序目录），中断后可重装 |
| 安装器返回非 0 | 保留安装包，下次启动提示"上次更新未完成，点此重试" |
| 绿色版（无卸载键） | 不自动更新，只提示"去下载页取新版" |
| 无管理员权限 | 无影响，per-user 安装不需要 UAC |
| 端口 8080 被占 / 服务未起 | 与更新无关，恢复后照常 |

## 9. 成本

**要钱，但很少。** 以 100 个用户、每人每月更新 2 次、包 55 MB 计：

| 项 | 单价 | 月用量 | 月成本 |
|---|---|---|---|
| 存储 | 0.118 元/GB/月 | 0.055 GB | ≈ 0.01 元 |
| 外网下行流量 | 0.5 元/GB | 11 GB | ≈ 5.5 元 |
| 请求 | 0.01 元/万次 | 几百次 | ≈ 0 元 |
| **合计** | | | **≈ 6 元/月，一年约 70 元** |

- 腾讯云 COS / 阿里云 OSS 都有**新用户免费额度**（历史上是几十 GB 存储 + 一定流量，够跑通早期），具体以当期官网活动为准，不依赖它做长期规划。
- 流量是唯一真实成本，和用户数线性增长：1000 用户 ≈ 60 元/月。
- **GitHub Releases 完全免费**，但 55 MB 包从 `objects.githubusercontent.com` 下来在国内经常龟速甚至断，更新失败率会明显偏高。适合做备用镜像，不适合做主源。
- **Gitee 发行版**免费、国内快，代价是要实名 + 仓库公开 + 发版审核。如果是开源的，这是性价比最高的免费方案。

### 实际选择：GitHub Releases

免费，且 `releases/latest/download/update.json` 这个地址永久有效。55 MB 包国内下载
不稳定是已知代价，靠客户端的失败重试 + 手动下载兜底。等用户量上来、失败率真的影响体验时，
**只改清单里的 `downloads` 数组加一个国内镜像即可，客户端一行不用动** —— 这正是当初把
「安装包地址」放进清单、而不是写进代码的价值。

## 10. 发布 SOP

```bash
# 1. 改 desktop/version.py 的版本号 + 在 版本更新说明.md 顶部加一版（顺序别反）
# 2. 一条命令：构建 + 生成清单 + 发到 GitHub Releases
cd 酷态科充电器控制\GitHub
.venv\Scripts\python.exe build_installer.py --publish
```

脚本自动完成：

1. 版本一致性门禁（`version.py` / `pyproject.toml` / `__init__.py` / 文档引用）
2. 打包 onedir → payload.zip → 安装器 → 归档 + 同步 `分发\`
3. 算 SHA256、写 `dist\update.json`（`notes` 从更新说明里自动摘小节标题）
4. `gh release create v<版本>` + 上传安装包和 `update.json`
5. 打印 release 页和清单地址

前置条件（只需一次）：

```bash
gh auth login                      # 登录 GitHub CLI
git remote add origin <你的仓库>    # 仓库必须是 public，否则 release 匿名拉不到
git push -u origin master
```

仓库地址会由脚本 `gh repo view` 自动写入 `desktop\updatecfg.py` 的 `REPO`，
不用手填；想指定别的仓库就手改那一行。

> **本项目当前配置（2026-11-06 打通）**
> 仓库：`lyy309335-ship-it/cuktech-charger-control`（public）
> 已写入 `desktop\updatecfg.py`：`REPO = "lyy309335-ship-it/cuktech-charger-control"`
> v1.7.0 已发布，清单地址固定为
> `https://github.com/lyy309335-ship-it/cuktech-charger-control/releases/latest/download/update.json`
>
> 实测算到的三个教训：
> 1. **`gh` 要带 `GH_TOKEN` 环境变量**。本机 keyring 在非交互 shell 里读不到，
>    `gh auth status` 会显示已登录但 `gh api` 报未登录，两者打架时以 `GH_TOKEN` 为准。
> 2. **`git push` 卡死是代理导致的，不是网络慢**。本机环境里有
>    `HTTPS_PROXY=http://127.0.0.1:2329`，git 会老老实实走这个代理然后挂住，
>    表现是几分钟无任何输出、最后 `SIGTERM` 或
>    `schannel: server closed abruptly (missing close_notify)`。
>    正确做法是**推之前把代理变量摘掉**：
>    ```bash
>    env -u HTTPS_PROXY -u HTTP_PROXY -u https_proxy -u http_proxy -u ALL_PROXY \
>        git -c http.version=HTTP/1.1 -c http.sslBackend=openssl push
>    ```
>    实测同一条命令从「卡 6 分钟被杀」变成「21 秒完成」。
>    `credential.helper='!gh auth git-credential'` 也会卡，别用，直接内嵌 token 推。
> 3. 构建收尾的「清理旧产物」会被本机安全策略直接掐进程，导致 `--publish`
>    跑完退出码是 1 —— **看日志结尾有没有打印 release 地址**，有就是成功，别被退出码骗了。

发完必须验一次：

```bash
curl -s https://github.com/<repo>/releases/latest/download/update.json
```

确认 `version` 是新版本号、`sha256` 与 `分发\CUKTECH-Setup_v<版本>.exe` 一致。

> **同一版本号不能发第二次**：脚本发现 tag 已存在会直接退出。
> 因为老客户端可能已经拿到了旧清单，同一个版本号两个不同包会让缓存和校验互相打架。
> 改坏了就发 1.7.1，不要重发 1.7.0。

## 11. 明确不做

| 不做 | 原因 |
|---|---|
| 后台静默升级 | 常驻托盘工具突然重启，用户会当成崩溃 |
| 灰度 / 分批放量 | 用户量不够，两层版本只增加支持成本 |
| 自动回滚（降级安装） | 版本号只升不降，回滚 = 发一个号更高的旧代码，简单且不会和"已升级"打架 |
| 增量更新（bsdiff） | 55 MB 全量下载在这个规模完全可接受，增量方案的补丁管理成本远高于省下的流量 |
| 代码签名证书 | 单年几千元，对个人分发不划算；SHA256 + HTTPS 已能防篡改，只是首次运行仍会被 SmartScreen 提示 |

## 12. 验收清单

- [ ] 装 v1.7.0 后，人为把 `update.json` 的 version 改成更高，托盘出现提示
- [ ] 点更新 → 自动装完 → 新版本号出现在运行管理里，`.env` 凭据和历史功率都还在
- [ ] 把 `sha256` 改错 → 提示校验失败，**不安装**，程序照常运行
- [ ] 断网启动 → 无任何弹窗，日志只有一行"检查更新失败"
- [ ] 24 小时内重复启动 → 不再发请求（看服务端访问日志）
- [ ] 用户关掉开机自启后更新一次 → 自启仍然是关的（§7 的修复）
- [ ] 绿色版启动 → 不尝试自动更新
- [ ] 更新过程中强制断电 → 再次启动能正常重装（覆盖安装可重入）
