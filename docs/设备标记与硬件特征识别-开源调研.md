## 二、"设备标记"在开源界的三种真实形态

### 形态 1｜给**充电器本身**起名（最接近截图里的「标记设备」按钮）

`kairui1108/cuktech-ble-server` 的配置页做到了这一步：

- 小米云扫码登录，勾选一台或多台充电器，**批量导入**它们的 MAC / Token / BLE Key
- 导入时**按 MAC 匹配**已有设备卡片 —— 同一台只更新凭据和名称，不会重复添加
- 设备名称可从米家云同步（多台时省事）
- 巴法云语音开关可以「一行一个」：自定义显示名 + 绑定到哪台设备 + 哪个端口

> 这就是「标记设备」的完整实现，但标记对象是**充电器**，
> 区分依据是 **BLE MAC 地址**（次要是米家云端设备名 `did`）。

### 形态 2｜多设备路由（`device_id` 维度隔离）

`kairui1108/cuktech-ble-ha` 的 `config.yaml` 加了 `devices:` 节：

```yaml
ble:                       # 永远 primary，device_id 固定 default
  mac: "AA:BB:CC:DD:EE:01"
devices:
  - id: desk               # 既是 topic 后缀也是设备标识
    name: "书桌充电器"
    mac: "AA:BB:CC:DD:EE:02"
```

- 每台独立的 BLE 连接 / 状态 / 会话 / 限额 / 历史（`history.db` 按 `device_id` 分区）
- Web UI 出现设备切换器（单设备时隐藏），HA 里一设备一 entry
- 明确标 **Beta**：两台真机并发认证互相干扰只能在 P5 canary 验证

> 关键点：README 早先写的是 "currently supports only one charger at a time"，
> 现在扩到多台 —— 但**区分依据始终是 MAC**，而不是任何电气特征。

### 形态 3｜充电会话记录（对应截图里的曲线 + 导出 CSV）

`kairui1108/cuktech-ble-server`：

- `/api/sessions` 自动记录充电会话（起止时间、充入电量、峰值功率）
- `/api/sessions/{id}/export` 导出**单个会话**的采样点 CSV
- `/api/export/{port}` 按「端口 + 时间窗」导出原始采样

> 截图里那块「时间轴 14:30→14:37 / 0.1 Wh / 均功率 0.9 W / 导出 CSV」
> 在开源界已有等价实现，唯独**没有**会话级的「这台设备是谁」标签。

## 三、结论：没有开源项目做「标记被充设备」

翻遍 31 个仓库的 README 和功能清单：

| 想做的事 | 开源界现状 |
|---|---|
| 标记**充电器**（起名、去重、多台切换） | ✅ 成熟，`kairui1108/cuktech-ble-server` 已实现，依据 = BLE MAC |
| 记录**充电会话**（曲线、电量、导出） | ✅ 成熟，同上，依据 = 端口 + 时间段 |
| 标记**接在口上的那台手机/耳机**，并按特征自动认出来 | ❌ **一个都没有** |

截图里「标记设备」标的是 `苹果无线充电`、下面配 `iPhone Air · 12.1Wh`、
「已保存，下次这台设备自动带出」—— 这是**受电设备**维度的身份，
在现有开源生态里**找不到任何现成实现**，要做只能从零设计。

## 四、如果真的要做，"硬件特征"实际能拿到什么

按「充电器这一侧能观测到的信号」从强到弱排：

### 1. 端口级电气特征（现在就能读到，最强）

| 特征 | 数据来源 | 区分力 |
|---|---|---|
| 协议类型 PD / PD Fixed / PD PPS / QC / SCP / UFCS / idle | `ports[x].protocol`（kairui1108 已在做） | 中：能分出「苹果无线充(PPS/PD)」 vs 「QC 耳机」 |
| 协商档位（受电设备请求的 PDO/RDO） | 电压 + 电流实际值 | **高**：iPhone 常见 9V/2.22A，笔电 20V/3.25A |
| 功率曲线形态 | 采样序列 | **很高**：无线充是脉冲，手机是恒流→恒压，笔电长期满载 |
| 电压纹波/跳变节奏 | 需要更高采样率 | 中：同一型号手机几乎一致 |

> 这组特征组合起来，区分「同一个口上是 iPhone 还是 MacBook、是无线充还是真机」
> 在原理上完全可行 —— PD 协商结果 + 曲线形态就是设备的"电气指纹"。

### 2. 插拔时序（时间维度，成本为零）

拔→插的间隔、首次协商耗时、功率爬升斜率、稳态维持时长。
同一台设备反复插入时这些量高度稳定，可与上表叠加提高置信度。

### 3. 充电器自身标识（区分"是哪台充电器"，不是"哪个手机"）

- **BLE MAC** —— 固定、唯一，开源界唯一实际在用的硬标识
- **米家 `did` / 云端设备名** —— 可从米家云同步，用户可改
- 本项目现有凭据体系里已经带了 MAC，做"多台充电器分身份"零成本

### 4. 拿不到的（别指望）

- 受电设备的 **MAC / USB 描述符 / 序列号**：充电器在物理层看不到。
  USB-C 充电时 CC 线上只跑 PD 报文，**不含任何设备身份字段**。
- 想要真身份只能加硬件：PD sniffer（如 Twinkie）或走 USB 数据线的 USB 枚举。

## 五、给本项目的落地建议（按成本递增）

### 方案 A｜端口 × 电气指纹自动关联（推荐先做，纯软件）

1. 每条充电会话落库时，顺带存下「首次协商档位 + 协议 + 峰值功率 + 曲线形态摘要」
2. 用户点「标记设备」→ 填名称 + 电池容量（Wh/mAh）→ 绑定到该指纹
3. 下次同口插入时算相似度（档位完全匹配 + 功率曲线 DTW 距离阈值），命中就自动带出
4. 命中率不够时降级为「按端口记住上次是谁」，用户可手动改

**风险**：同一型号两台手机无法区分（指纹相同），这是物理上限，要在 UI 上说明。

### 方案 B｜蓝牙信标辅助（需要被充设备配合）

手机装个广播 App，充电时广播一个自定义 UUID，充电器侧 BLE 扫描到就认人。
**问题**：本项目已在用 BLE 连充电器，同适配器再扫描会抢带宽，实测容易掉连接。

### 方案 C｜PD sniffer 硬件（最准，但要拆线）

在充电线与手机之间串一个 PD 分析器，抓完整 PD 报文（含 SVDM 里的厂商信息）。
成本与体积都不适合消费级产品，只适合做验证。

## 六、与本项目现状的差距

本项目（v1.6.0）目前：

- ✅ 已有四口实时功率、协议识别、充电历史曲线、CSV 导出
- ✅ 已有 BLE MAC 凭据体系（`CUKTECH_DEVICE_MAC`），做多台充电器分身份零成本
- ❌ 没有「充电会话」概念（只有按秒采样，没有起止/电量聚合）
- ❌ 没有设备标记、没有指纹匹配

要往截图那个方向走，**第一步不是做标记 UI，而是先补"充电会话"这一层数据模型** ——
没有会话，就没有地方挂"这台是谁"的标签。会话表 + 指纹字段是后面一切的地基。
